# 0003 模型包与前端的分工

- 状态：已采纳（用户 2026-10-25 确认）；"前端怎样拿到模型包"按用户 2026-10-26 的方向定为 B
- 相关：
  - 引擎的方向见 [0001](0001-engine-direction.md)，能力清单见 [0002](0002-capabilities.md)；
  - 前端组件的方案见 [docs/frontend.md](../frontend.md)（§5 分步、§6 已定的细节；原是 vue-tsx-pro 的 WORKFLOW.md），底座的进度在 vue-tsx-pro 的 ROADMAP 阶段 9。

## 背景

流程定义、运行时类型（实例、待办、流转记录）和校验原来写在 vue-tsx-pro 的 `@vue-tsx-pro/ui/workflow` 里，注明"后端引擎照这里实现"。
但 TypeScript 后端跑在 Nuxt、Nest 这类服务端框架里，不应为了几个类型和校验函数依赖一个 Vue 组件库；Java 后端也要一份同样语义的实现。

## 决定

| 项 | 决定 |
| --- | --- |
| 模型包 | 契约放本仓库的零依赖模型包：流程定义、运行时类型、校验与问题代号、条件求值与连线副作用、图的索引、两个版本的差异。TS 与 Java 各一份，共用一套样例（定义 + 期望的问题、条件 + 变量 + 期望的结果），同 query 的金样例做法 |
| 问题代号 | 校验只给代号和参数，文案在前端的语言包里；发布时后端用同一份规则再校验一遍 |
| 前端组件 | 通用的底座（画布、撤销重做、条件构造器、人员与组织选择器）放 vue-tsx-pro 的核心与 `/diagram` 子路径；流程图、设计器、审批面板、收件箱这些流程组件按模型包的类型工作 |
| 管理端页面 | 定义管理、实例监控、作业、工作日历这些直接对接引擎接口的页面放本仓库，用 vue-tsx-pro 搭 |
| 顺序 | 前端先做画布底座与通用输入（不依赖模型包），再建模型包，然后重做流程组件和运行时组件 |

## 前端怎样拿到模型包（2026-10-26 定为 B）

vue-tsx-pro 是公开仓库，CI 要能安装全部依赖；本仓库是私有的，模型包暂不发布。流程组件开始改用模型包（frontend.md §5 第 3 步）之前要定下来：

| 做法 | 好处 | 代价 |
| --- | --- | --- |
| A. 流程组件留在 vue-tsx-pro 的 `/workflow`，模型包发布到 npm（0.x） | 文档站照常演示流程组件；组件库的使用方直接装 | 模型包要先发布，契约每改一次都要发版，跨两个仓库同步 |
| B. 流程组件挪到本仓库（例如 `@zerodep-dev/flow-ui`），vue-tsx-pro 只留通用底座 | 契约、两个后端、流程组件在一个仓库里，一次提交改完；vue-tsx-pro 不再依赖引擎 | 本仓库要有前端的构建与演示页（可以用 vue-tsx-pro 的 `/docs-kit`），vue-tsx-pro 改了底座要重新打包给本仓库用 |

用户 2026-10-26 的方向：vue-tsx-pro 与 query 由用户手动发布到 npm、Maven，本仓库把它们当普通依赖开发，引擎自己也打包发布
（后端支持 Nuxt、Next 这类 Node 框架与 Java Spring，前端用 vue-tsx-pro 的技术栈）。因此取 B：

- vue-tsx-pro 只留通用底座（画布、撤销重做、条件构造器、人员与组织选择器、FilterBar 的高级筛选），现有的 `/workflow` 子路径
  （FlowDiagram、FlowDesigner、ApprovalActions 等）已于 2026-10-26 整个删除（连同文档站的“流程”分类；旧实现在 vue-tsx-pro 的提交 `f7bfdc2e`），流程组件在本仓库按模型包重做，界面风格与新的画布一致；
- 组件库暂时缺的能力，本仓库像 vue-tsx-pro 的文档站那样用 `@vue-tsx-pro/tsx` 的编译插件直接编译自己的 TSX 补上，不必等组件库发版；
- 条件树与组件库的 `Condition`（`{ field, op, value }` 加 all / any / not）同形，模型包定稿时把流程定义里的 `var` 对齐成 `field`。
