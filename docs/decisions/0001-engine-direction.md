## 定位

- **通用的审批流程引擎**，有很强的自定义扩展能力。具体业务（单据、字段、组织架构）都不进本仓库，只通过扩展点接入。
- **标准行为都能替换**（用户 2026-10-26，所有设计都守这一条）：引擎内置的每一种标准行为（存储、编号、时钟、工作日、处理人解析、通知、作业调度、表单运行时……）都放在接口后面，
  接入方不满意就换成自己的实现；能用泛型表达的（用户、业务编号的类型）用泛型。Java 用接口加 Spring 的默认实现（`@ConditionalOnMissingBean`），TS 用选项传实现。每份决定文档单列"可替换的部分"。
- **两个后端，同一份语义**：
  - Java 版接 Spring Boot；
  - TypeScript 版接 Nuxt（目前只支持这两种）。

  两版读同一份流程定义、写同一套表，行为由共享的场景用例保证一致（同 query 的金样例做法）。
- **前端**用 vue-tsx-pro 搭。契约放本仓库的零依赖模型包，前后端都按它；分工见 [0003](0003-model-and-frontend.md)。
- **依赖方式**：query、vue-tsx-pro 都按发布的包依赖（npm 上已有 `@zerodep-dev/vue-tsx-pro-*` 0.1.0、`@zerodep-dev/query-*` 2.0.0），query 的 Java 包已发到 Maven 中央仓库（2.0.0）；要先改 query 时用本机 `mvnw install` 的 SNAPSHOT（2026-10-26 更新）。

## 初步方向（已定：第 1、2 条见 0005，第 5 条的扩展点见 0006）

1. **模型是图**，即泳道、节点和连线（BPMN 子集），以 vue-tsx-pro 的 `ProcessDefinition` 为基础扩展。（已定，见 [0005](0005-definition.md) 第 1 节）
   - 不用节点树的原因：需求里有带轮次的循环（第 N 轮自动提级）、退回到指定节点、提级、并行汇合，节点树表达不了。
   - 图的风险用发布时的结构校验兜住：分叉与汇合配对、走不到结束、退回目标在上游。校验规则前后端共用一份清单。
2. **定义发布后不可变**。一行就是一个版本，模型整份存 JSON。进行中的实例按发起时的版本走完。草稿单独存，可以反复编辑。（已定，见 0005 第 1 节；草稿与表单共用 `flow_draft`，见 0004 的 5.2）
3. **一次操作一个事务，并发靠数据库保证**（已定，用户 2026-10-26）（2026-10-24 已在 query 的实库场景里于五个库上验证，见 query 的场景对照"流程引擎的写法"）：
   - 每个操作的第一条语句是 `UPDATE flow_instance SET rev = rev + 1 WHERE id = ?`。它在各库上都锁住实例行（SQLite 直接拿到写锁），后来的推进在这里排队，之后的读都能看到前一个事务提交的结果。
     会签的两个待办同时提交时，只推进一次；不先锁的话，两边都以为对方没完成，流程会卡住（warm-flow 的缺陷）。
   - 隔离级别不要依赖：云上 PolarDB 默认读已提交，社区 MySQL 是可重复读。宿主事务里先做过普通查询时，可重复读下的普通读会拿到旧快照，所以引擎的关键读放在锁住实例行之后。
   - 提交待办用带状态条件的更新（`… WHERE id = ? AND state = 'open'`，改到 0 行就是重复提交）；
   - 事务边界：Java 用 `SpringConnections.of(dataSource, transactionManager)`，引擎自己调用 `db.transaction(...)`，已有同一个事务管理器的事务时加入。使用方都是多数据源，跨库时由使用方外层的编程式事务包住。
4. **定时、超时、提醒、无人认领的兜底都进一张作业表**（已定，用户 2026-10-26）：
   - 工作进程先普通读出到期的候选，再逐个用 `UPDATE flow_job SET locked_by = ?, locked_until = ? WHERE id = ? AND (locked_by IS NULL OR locked_until < 现在)` 抢占，改到 1 行才算领到；失败重试。
   - 不用 `FOR UPDATE SKIP LOCKED`：实测 InnoDB 会锁住扫描到的每一行，没有合适的索引时第一个进程就锁住整张表，第二个进程什么也领不到，而 PostgreSQL 只锁返回的行。
   - 工作日按工作日历计算。
5. **扩展点**：
   - 处理人解析：部门、角色到人（标准组织模型是用户、部门、角色；岗位等由接入方绑定到角色或扩展），以及部门负责人、上级第 N 级；
   - 业务守卫：流转前的校验，例如材料是否齐全；
   - 自动节点的动作：例如一个流程走完后生成另一个流程的实例；
   - 条件里的自定义判断：写成计算值 `fn.名字`（0005 的 6.1）；
   - 监听器：分事务内和提交后两种；
   - 操作拦截：权限、审计；
   - 通知渠道；
   - 待办查询的业务摘要列：使用方按业务编号连接自己的表。

   定义里只写名字，不写脚本；实现由使用方在代码里注册，两个后端的名字和语义相同。

## 表的草案（已由 [0007](0007-tables.md) 接替，这里留作对照）

- 表名用 `flow_` 前缀加小写下划线；InnoDB，utf8mb4。

### 流程变量的存法（用户 2026-10-24 选定 A）

流程变量是推进流程用的数据：条件判断的输入、协商轮次之类的计数、派单时选定的团队、会签的参与人列表。

| 维度 | A. 实例上一个 JSON 列 | B. 单独的变量表（每个变量一行，按类型分列） |
| --- | --- | --- |
| 读 | 和实例行一起读出来，一次到位 | 多一次查询，按实例取出所有行再拼成对象 |
| 写 | 整份写回（实例行已经锁住，没有并发问题） | 只写改了的变量，要用插入或更新；PolarDB 小版本未知，这个写法本身依赖兼容模式 |
| 类型 | JSON 只有字符串、数字、布尔、数组、对象；日期按 ISO 字符串；小数解析成浮点数，金额要按字符串或整数分存 | 每种类型一列（文本、整数、定点小数、时间、布尔，复杂值另放 JSON 列），精度和比较都准确 |
| 按变量筛选实例 | `JSON_EXTRACT` / `->>` 能写，但只有事先知道的键能建函数索引，任意键的筛选会全表扫 | 按（变量名, 值）建索引，任意变量都能高效筛选；query 已有这类查询的写法（测试夹具 `Workflow`） |
| 按节点区分（每个会签人的投票） | 放进待办自己的 JSON 列 | 表里多一个待办列 |
| 变更历史 | 记进流转记录的附加数据 | 同左，或再加一张历史表 |
| 两个后端的一致性 | 简单：两边都是同一份 JSON | 要约定类型代码和各列的取值规则，两边严格一致 |
| 复杂度 | 低 | 中 |

- **建议选 A。**业务数据（件号、金额、供应商）放在业务表里，列表筛选和报表都从业务表走；流程变量只用来推进流程，几乎不需要按它筛选。
- 以后真的要按变量筛选时可以补一张"可检索变量"的投影表：定义里声明哪些变量要检索，引擎写变量时同步写进这张表。这样 A 的简单和 B 的可检索可以兼得，不用改原来的存法。
- 选 B 的理由只有一个：预计会有不依赖业务表、按任意变量查实例的通用页面（例如管理员按变量搜流程）。

### 场景用例的格式

```jsonc
{
  "name": "会签有人否决时立即结束",
  "definition": "definitions/sign-veto.json",     // 或直接内联
  "form": "forms/purchase.json",                  // 可选：字段清单（场景里不跑表单代码）
  "clock": "2026-10-24T08:00:00Z",                // 固定时钟；步骤里可以 "advance": { "workdays": 2 }
  "actors": { "alice": { "roles": ["finance"] }, "bob": {} },
  "steps": [
    { "as": "alice", "command": "start", "args": { "key": "sign-veto", "form": { "amount": "1200.00" } },
      "expect": { "workItems": [{ "node": "sign", "assignee": "bob", "state": "open" }] } },
    { "as": "bob", "command": "complete", "args": { "workItem": "$.workItems[0]", "outcome": "reject" },
      "expect": { "instance": { "status": "completed", "result": "rejected" }, "events": ["workItem.completed", "instance.finished"] } }
  ]
}
```

- 编号用测试用的 `IdStrategy`（按顺序发号），时钟用固定的 `Clock`：两个后端跑出来的结果逐字段可比——这也是"标准行为都能替换"的用处。
- `"$.workItems[0]"` 引用前一步的结果；`expect` 只比写出来的字段。
- Java 用 JUnit 的参数化测试、TS 用 `node:test` 逐个文件跑；新加一个场景只加一个 JSON 文件。
- 落地（2026-10-26，③b）：格式细化后写在 [spec/scenarios/README.md](../../spec/scenarios/README.md)（先发布的表单与流程、步骤的 `id` 与 `$名字.路径` 引用、按线上 JSON 比较）；Java 的执行器在 `java/flow-it` 的 `scenario` 包。

## 雪花的机器号（已定，用户 2026-10-26 按推荐定）

| 项 | 做法 |
| --- | --- |
| 默认：数据库里租用 | 表 `flow_worker`（机器号、持有者、租约到期时间、最后发号时间）。启动时用带条件的 UPDATE 抢一个空闲或过期的机器号（同作业的抢占写法，0001 第 4 条），之后定时续约 |
| 配置写死 | `flow.ids.worker-id = 7`：固定部署、机器号由运维分配时用，不碰 `flow_worker` |
| 替换 | `WorkerIdProvider` 接口：例如 Kubernetes StatefulSet 的序号、配置中心发的号 |
| 规则可调（用户 2026-10-26） | 雪花与大雪花**都一样**：机器号由哪几段组成（只有机器号，或区域号加机器号）、每段几位、怎样取得，都按配置或接口定。位布局写成 `SnowflakeLayout`（起始时间、时间单位、各段位数；雪花总共不超过 63 位，大雪花不限），机器号的每一段由一个 `WorkerIdProvider` 给出；内置的租用、写死两种只是默认实现 |
| 防重复 | 续约失败超过租约时长，停止发号并报错，不冒险继续；接手一个过期的机器号时，等时钟走过上一任记下的"最后发号时间"再发号 |
| 时钟回拨 | 同 0006 的 6.1：等时钟追上（默认）、报错、借用序号 |
| 大雪花 | 同样的租约；区域号、机器号的位数按大雪花的布局配置，区域号写在配置里 |
