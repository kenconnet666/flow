# 0004 表单：代码表单加拖拽设计器

- 状态：已定（用户 2026-10-26，逐节讨论定稿）。形态：表单写成 TSX 代码，注册后运行时编译；拖拽设计器生成代码，代码也可以自由修改。剩下的只有"待实测"两项
- 相关：0001 的"灵活表单"一行（本文接替它）；0002 的校验（表单是否已注册）与第 12 节；前端方案 [frontend.md](../frontend.md)

## 背景

审批节点要展示与填写业务表单，不同节点对同一张表单的字段有不同权限（只读、隐藏、可改、必填）。表单的作者有两类：
开发人员要写联动、远程数据、自定义校验；业务管理员要能自己拖出一张简单表单。两类人改的是同一张表单，不能各存一份。

可选的做法：

| 做法 | 问题 |
| --- | --- |
| JSON 配置表单 + 设计器 | 复杂联动、远程数据要靠配置项一项项加，最后变成用 JSON 写程序 |
| 纯代码表单 | 业务管理员改不了；引擎读不出有哪些字段 |
| 设计器只生成一次代码，之后手改（单向） | 手改过的表单再也回不到设计器 |
| **代码是唯一的来源，设计器读写同一份代码（双向）** | 设计器只能理解代码的一个子集，子集以外的部分要原样保留——下文的做法就是为此 |

## 已定

| 项 | 决定 |
| --- | --- |
| 来源 | 表单只存一份 TSX 源码。设计器打开时解析源码，拖拽、改属性都是改源码；手改代码后设计器重新解析显示 |
| 编译 | 保存时在浏览器的 Worker 里编译（`@zerodep-dev/vue-tsx-pro-tsx/compiler` 的 `compile`，同文档站演练场），源码与编译结果一起存。运行时只执行编译结果，审批页面不带编译器 |
| 依赖 | 表单代码只能导入登记过的模块：vue、vue-tsx-pro 的入口、接入方注册的业务组件与工具（同演练场的模块表 `run.ts`）。导入了没登记的模块，保存时报问题 |
| 后端代码 | 同前端一样在线编辑、存数据库、后端启动时加载；Spring Boot 的用 Java 写，Nuxt 的用 TS 写（用户 2026-10-26，细节见 1.5） |
| 分工 | 设计器里点得出来的只覆盖常见情况；复杂的自己改代码，前端改表单源码，后端写表单的后端代码（1.5）。设计器不追求把复杂写法也做成按钮（用户 2026-10-26） |
| 写进业务表 | 不做运行时映射；后端代码页签里"按业务表生成"按钮：选表、选列后生成 `load` / `submit` 的代码（用 query 写），生成后照常能改（用户 2026-10-26） |
| 顺序 | ① 讨论完 0001、0002 的契约 → ② 模型包 → ③ 最小链路（Java 后端 + `flow-ui/form` 手写代码表单走通审批）→ ④ Nuxt 后端跟上 → ⑤ 流程图与流程设计器 → ⑥ 表单设计器；组件库的两个新入口（vue-tsx-pro ROADMAP 9.8）随时单独做，最晚在 ③ 之前（用户 2026-10-26） |

## 方案

### 1. 表单文件的约定（已定，用户 2026-10-26）

一张表单由三部分组成：TSX 模块里的字段清单 `fields` 与默认导出的表单组件（下面的例子），加上可选的后端代码（1.5）。
设计器只改前两样里的常见写法；后端代码只在代码里写。

```tsx
import { defineFields, defineFlowForm } from '@zerodep-dev/flow-ui/form';
import { FormSection, NumberField, PeoplePicker, TextField } from '@zerodep-dev/vue-tsx-pro-ui';

/** 字段清单：只能是字面量（见 1.2） */
export const fields = defineFields({
  title: { label: '标题', type: 'text', required: true, maxLength: 50 },
  amount: { label: '金额', type: 'decimal', scale: 2, min: '0' },
  buyer: { label: '经办人', type: 'people', types: ['user'], max: 1 },
  lines: {
    label: '采购明细',
    type: 'list',
    minItems: 1,
    fields: {
      item: { label: '物品', type: 'text', required: true },
      quantity: { label: '数量', type: 'number', integer: true, min: 1 },
    },
  },
});

export default defineFlowForm(fields, ({ form, context }) => {
  // 这里可以写任意逻辑：远程数据、计算、监听；设计器不碰
  return () => (
    <form.Form>
      <FormSection title="基本信息">
        <form.Field name="title"><TextField /></form.Field>
        <form.Field name="amount"><NumberField /></form.Field>
        <form.Field name="buyer"><PeoplePicker source={context.people} /></form.Field>
      </FormSection>
    </form.Form>
  );
});
```

（`decimal` 字段用组件库的 `NumberField`，`form.Field` 按字段类型设好 `valueType`；明细表的写法见 2.1。）

#### 1.1 三部分各管什么

| 部分 | 管什么 | 谁读 | 设计器里 |
| --- | --- | --- | --- |
| `fields` | 数据的形状：有哪些字段、类型、必填与范围。**不管长什么样、怎么联动** | 引擎（提交时校验值与权限、值存进 `flow_form_data`）、流程设计器（节点字段权限、连线条件的字段列表）、表单设计器（字段列表）、`defineFlowForm`（生成 zod schema） | 全部能点 |
| 默认导出 | 长什么样、怎么交互：布局、控件、联动、远程数据、前端的跨字段校验 | 表单容器（审批页面里渲染） | 常见的能点（第 2 节），其余改代码 |
| 后端代码（可选） | 带出初始值、后端校验、后端算的字段、同事务写业务表、给前端调的接口 | 引擎（发起、暂存、提交时调用） | "后端代码"页签里写代码，没有可点的 |

- `defineFields` 只是给类型推断用的恒等函数（参数类型用 `const` 泛型），`form.Field` 的 `name` 因此能补全、写错报错，值的类型也从清单推出。
- `defineFlowForm(fields, setup)`：按清单生成 zod schema 交给 `useForm`，标签、必填标记、长度与范围都从清单来，`form.Field` 不用再写 `label`；
  `setup` 拿到 `form`（`useForm` 的控制器）与 `context`（容器给的：实例与节点信息、人员数据源、当前模式是填写还是查看），返回渲染函数。
  跨字段校验、单字段异步校验照常写在 `defineFlowForm` 的第三个参数里（`validate`、`dependencies`，同 `useForm`）。
- 节点上的字段权限由容器经 `context` 交给 `form.Field`，表单代码里不写节点判断（第 4 节）。

#### 1.2 字面量的限制

`defineFields(...)` 的参数必须是 **JSON5 值**：对象、数组、字符串、数字、`true` / `false` / `null`，可以有注释、尾逗号、不加引号的键。
不能出现变量、函数调用、展开（`...`）、计算的键、模板字符串、正则、`undefined`。不满足时保存报问题，指出位置。

为什么非要字面量：

1. **设计器要能改它**。拖进一个控件就是往这个对象里加一项、改属性就是改一个值；求值得到的结果写不回源码。这是决定性的理由。
2. **不执行代码就能读**。保存时在浏览器里静态提取成字段清单 JSON 存下；TS 后端要核对时也只需解析、不用执行。
3. **规则一句话说得清**。"JSON5 值"是现成的、开发人员熟悉的定义，不用另写一份"哪些写法可以"的清单。

限制挡住的写法，各有去处：

| 想写的 | 去处 |
| --- | --- |
| 几个字段共用一份选项 | `options: { source: '供应商等级' }`：选项来自接入方登记的字典（前端加载、后端校验值在不在字典里）；或者各写一份 |
| 选项随别的字段变（省 → 市） | 清单里写字典 `source`，过滤写在渲染代码里；后端只校验值在字典里 |
| 条件必填、跨字段规则 | 前端写在 `validate` 里（即时提示）；后端要拦的写在后端代码的 `validate` 里（1.5）。后端不重跑前端代码 |
| 算出来的字段（合计） | 清单里声明这个字段，前端算出来给人看；后端代码的 `compute` 重算并覆盖，不信前端交上来的数 |
| 多语言的标签 | 暂时只有一种语言；以后要时 `label` 改成语言包的键（待定） |

**两边不一致的兜底**：运行时表单加载后，把模块真正导出的 `fields` 和存下的清单比一遍，不一致就不渲染并报问题（正常保存不会出现，防的是绕过保存流程或提取有 bug）。

#### 1.3 字段类型

类型名与条件构造器的 `ConditionFieldType` 对齐，能参与条件的直接对上；值都是 JSON，后端两种语言读法一致。

| 类型 | 值（JSON） | 专有属性 | 条件里当作 |
| --- | --- | --- | --- |
| `text` | 字符串 | `minLength`、`maxLength`、`pattern`（正则写成字符串） | `text` |
| `number` | 数字 | `min`、`max`、`integer` | `number` |
| `decimal` | **字符串**（`"19.90"`） | `scale`（小数位）、`min`、`max`（也写成字符串） | `number` |
| `boolean` | 布尔 | — | `boolean` |
| `date` | `"2026-10-26"` | `min`、`max` | `date` |
| `datetime` | 带 `Z` 的 ISO 8601（同 0001 的时间约定） | `min`、`max` | `date` |
| `select` | 选项的值；`multiple` 时是数组 | `options`（字面量列表或 `{ source }`）、`multiple` | `select` |
| `people` | `PeopleEntry` 的数组（同组件库的 `PeoplePicker`：带名字，回显不用再查） | `types`（user / department / position）、`max` | `select`（只比较 id）；可作为处理人来源（同 0002 §3"流程变量里的人"，取 `form.字段名`） |
| `file` | `{ id, name, size }` 的数组，文件本身由接入方存 | `accept`、`maxCount`、`maxSize` | 不参与 |
| `list` | 对象的数组（明细行） | `fields`（一层，里面不能再有 `list`）、`minItems`、`maxItems` | 不参与（以后要时加"行数""某列合计"） |

- 所有字段都有：`label`（必填）、`description`、`required`、`default`（同样是字面量），以及 `visibleWhen`、`requiredWhen`。
- `visibleWhen`（显示条件）、`requiredWhen`（必填条件）的值是条件树，与组件库的 `Condition` 同形，本身是 JSON5 字面量。放在清单里而不是 JSX 上，是因为它影响数据是否有效：
  前端按它显示或隐藏、标必填；后端用模型包的条件求值再校验一次——条件不成立时这个字段不算必填，交上来的值丢掉。
  节点上的字段权限（第 4 节）优先：节点上隐藏的字段，条件成立也不显示。（2026-10-26 随第 2 节补入）
- `decimal` 用字符串：金额在 JS 里用浮点会丢精度，Java 用 `BigDecimal` 读；组件库已有按文字读数字的 `isNumericText`。
- 字段名：`^[a-z][A-Za-z0-9]*$`，最长 64，同一层里唯一。字段名会出现在条件里（写成 `form.字段名`，如 `form.amount`）、节点权限与摘要里，所以发布后改名等于删一个、加一个，校验会指出引用了旧名字的流程。
  表单的值不放进流程变量，单独存（5.5）。（2026-10-26 随第 5 节调整）

#### 1.4 提取放在哪

静态提取要解析 TSX（Babel），而模型包是零依赖的，所以分两处：

- **模型包**（TS 与 Java 各一份）：字段清单的类型、清单本身的校验（类型、属性、字段名）、按清单校验提交的值与权限、问题代号。
- **前端的表单工具**（本仓库的前端包，用组件库已有的 Babel 编译器）：从源码里提取清单、写回清单、编译。TS 后端要核对源码与清单时可以复用它，Java 后端只读存下的清单 JSON。

#### 1.5 表单的后端代码

和前端代码一样**在线编辑、存在数据库里**，后端启动时加载（用户 2026-10-26 定）。后端只支持 Spring Boot 与 Nuxt，
**各用自己的语言**：Spring Boot 的用 Java 写，Nuxt 的用 TS 写。一个部署只有一种后端，所以一张表单的后端代码只有一份，语言跟着部署走。

一张表单的后端代码是一个处理器，引擎在固定的时机调它；每个方法都可选，没有后端代码时只做清单级的校验。

```java
// Spring Boot：一个 public 类，不写 package（引擎给每个版本单独的类加载器，类名不会冲突）
import org.dpdns.zerodep.flow.form.*;
import org.springframework.beans.factory.annotation.Autowired;

public class PurchaseForm implements FormHandler {
    @Autowired BudgetService budgets;   // 接入方自己的 Spring Bean，照常注入

    @Override
    public FieldErrors validate(FormValues values, FormContext ctx) {
        return budgets.remaining(ctx.department()).compareTo(values.decimal("amount")) < 0
            ? FieldErrors.of("amount", "超出预算")
            : FieldErrors.none();
    }
    // load、compute、submit、actions 都是默认方法，按需覆盖
}
```

```ts
// Nuxt：默认导出一个处理器；import 只能取登记过的模块（同前端的模块表）
import { defineFormHandler } from '@zerodep-dev/flow/form';
import { budgets } from '#flow-modules/budget'; // 接入方登记的服务

export default defineFormHandler({
  load: async (ctx) => ({ buyer: [await ctx.currentUserEntry()] }),              // 发起时带出初始值
  validate: async (values, ctx) => ((await budgets.remaining(ctx.department)) < values.amount ? { amount: '超出预算' } : {}),
  compute: (values) => ({ total: sum(values.lines) }),                            // 后端算的字段，覆盖前端交上来的
  submit: async (values, ctx) => { await ctx.db.insert(/* ... */) },              // 与流转同一个事务，失败整个回滚
  actions: { remainingBudget: async (args, ctx) => budgets.remaining(args.department) }, // 前端 context.call('remainingBudget', args)
});
```

| 项 | 做法 |
| --- | --- |
| 调用时机 | `load`：发起、打开草稿时；`validate` → `compute` → 清单与权限校验 → `submit`：提交时，在流转的事务里依次执行；暂存只做清单校验 |
| 给前端的接口 | `actions` 经引擎的接口暴露，调用前查看权限（能看这个实例的人才能调）；前端表单用 `context.call(名字, 参数)`，不用自己拼地址 |
| 编辑 | 表单设计器里多一个"后端代码"页签（同一个代码编辑器，Java / TS 语法）；"试编译"把源码交给后端编译，错误带行列号标在编辑器里。编译不过不能发布 |
| 加载 | 启动时把所有已发布版本的后端代码一次编译、加载；某一张编译失败只让这张表单不可用并记日志，应用照常启动（可配置成启动失败） |
| 刷新 | 本实例发布后立刻换上新版本。集群里通知其他实例由接入方自己接（Kafka、Redis Stream 或别的消息队列），引擎只给扩展口与示例（用户 2026-10-26），见下面"集群里的刷新" |
| 表单改版 | 后端代码跟着表单版本走（存在同一行版本里），进行中的实例用它发起时的版本，前后端代码总是配套的 |
| 类型 | 字段清单能生成 Java record 与 TS 类型给后端代码用（编辑器里也有补全）；不用也能经 `FormValues` 按名字取 |
| 导出 | 表单（前端源码、后端源码、清单）能导出成文件、再导入，用于版本管理与在开发环境里调试 |

两种后端怎样编译、执行：

| | Spring Boot（Java） | Nuxt（TS） |
| --- | --- | --- |
| 编译 | JDK 自带的 `javax.tools.JavaCompiler`，支持完整的 Java 语法（17）。classpath 取应用自己的类加载器（Spring Boot 的嵌套 jar 要自己实现 `JavaFileManager` 列出类，可参考 Liquor 的做法，待实测） | 去掉类型（`oxc-transform` 或 esbuild 一类，只转换、不做类型检查），import 换成从模块表取（同前端） |
| 执行 | 每个版本一个类加载器加载编译出的类，用 Spring 的 `AutowireCapableBeanFactory.createBean` 实例化，`@Autowired` 照常注入；换版本时丢掉旧的类加载器 | 在本进程里执行（`new Function` 加模块表，同演练场的做法；服务端不受页面的内容安全策略限制） |
| 运行环境要求 | **运行时要有 `jdk.compiler` 模块**：用 JDK 镜像，或用 jlink 打包时带上它；只有 JRE 的镜像（如 `eclipse-temurin:17-jre`）编译不了（用户 2026-10-26 接受）。启动时缺这个模块就报清楚的错，不等到编译时才失败 | **只能部署成 Node 服务**（Nitro 的 node-server 预设）；Cloudflare 一类边缘运行时禁止动态执行代码 |
| 能调什么 | 应用里所有的类与 Bean | 只有接入方登记进模块表的服务、工具，加上引擎给的 `ctx` |

集群里的刷新（引擎不带消息队列，只给两个口子）：

| 口子 | Spring Boot | Nuxt |
| --- | --- | --- |
| 发出：本实例发布了新版本 | 接入方实现 `FormChangeBroadcaster` 的 Bean，`published(formKey, version)` 里发消息；没有这个 Bean 时什么都不发 | 引擎选项 `onFormPublished(formKey, version)` |
| 收到：别的实例发布了 | 接入方的消费者调 `flowForms.reload(formKey, version)` | 同左，`engine.forms.reload(formKey, version)` |

- `reload` 是幂等的：已经是这个版本或更新的就什么都不做；消息重复、乱序都没关系。
- 消息丢了也不会一直错下去：下次重启会加载最新版本；管理端另有"重新加载"按钮（调同一个 `reload`）。
- 不接任何消息队列时，单实例部署照常工作；多实例时其他实例要等重启才换版本。
- 示例只放文档与示例项目，不进引擎的依赖：Spring Boot 用 Redis Stream 与 Kafka 各一个，Nuxt 用 Redis Stream 一个。
- 流程定义发布后如果各实例有缓存，也走这两个口子（`published` / `reload` 带上种类：表单或流程定义），不另做一套。

参考：Java 里把脚本存在数据库、运行时加载的规则引擎 LiteFlow，Java 脚本先用过 Janino（只支持部分 Java 语法，已不推荐），后改用基于 `javax.tools` 的 Liquor，文档写明必须在 JDK 环境下运行、不能用 JRE。

安全见第 6 节：不做隔离，后端代码以应用的全部权限运行；页面与接口的安全由接入方的框架负责，引擎只给扩展点与文档提示。

### 2. 设计器能理解的子集（已定，用户 2026-10-26）

设计器只做常见的：拖控件、排布局、改字面量属性、改字段清单。认不出的写法不报错、不改写，当成代码块原样保留，复杂的回到代码里改。

| 代码 | 设计器里 |
| --- | --- |
| `fields` 里的每一项 | 字段列表；增删改直接改这个对象字面量 |
| JSX 里登记过的组件（布局：表单、分组、栅格、标签页；字段：`form.Field` 加输入控件；展示：文字、分割线） | 画布上可拖动、选中、改属性的块 |
| 属性是字面量（字符串、数字、布尔、简单 JSON） | 属性面板里按类型编辑 |
| 属性是表达式（`disabled={amount.value > 100}`） | 属性面板里显示为"代码"，只能改那一小段代码 |
| 没登记的元素、`{条件 && ...}`、`{list.map(...)}` | 一整块"代码块"：能移动、删除，内部只能在代码里改 |
| 渲染函数以外的代码、注释、空行 | 不显示，原样保留 |

#### 2.1 面板里能拖的组件

全部用 vue-tsx-pro 现有的组件；面板按四类排。

| 类 | 组件 | 能改的常见属性 |
| --- | --- | --- |
| 布局 | 分组 `FormSection`、栅格 `Grid` / `GridItem`、标签页 `Tabs`、分割线 `Separator` | 标题、说明；列数、间距、跨列；各页的标题 |
| 展示 | 文字 `Text`、提示 `Alert` | 内容、色调 |
| 字段 | `form.Field` 加一个输入控件，按字段类型选（下表） | 字段的属性改清单，控件的属性改 JSX（2.3） |
| 业务 | 接入方登记的组件（2.4） | 登记时声明的 |

字段类型能用的控件，第一个是默认：

| 字段类型 | 控件 |
| --- | --- |
| `text` | `TextField`、`Textarea` |
| `number` | `NumberField`、`Slider`、`Rating`（只限 `integer`） |
| `decimal` | `NumberField`（值是 `Decimal`；表单容器在边界上与清单的字符串互转） |
| `boolean` | `Switch`、`Checkbox` |
| `date` | `DatePicker`、`DateField` |
| `datetime` | `DatePicker`（`granularity="minute"`；控件给的是本地时间，容器按处理人的时区与清单的 UTC 互转） |
| `select` | 单选：`Select`、`RadioGroup`、`ToggleGroup`；`multiple`：`Select`、`CheckboxGroup`、`Transfer`；字典是树形的：`TreeSelect`、`Cascader` |
| `people` | `PeoplePicker` |
| `file` | `Upload`、`FileDrop` |
| `list` | 明细表 `form.List`：本仓库新做，建在 `form.array` 与组件库的表格上；列就是子字段，每列的控件同上表；增删行、排序、最少最多行数从清单来 |

#### 2.2 拖拽与字段清单的联动

- 从面板拖一个字段控件进画布：清单里加一项（名字先生成 `field1`，类型按控件），JSX 里插 `<form.Field name="field1">`；名字和标签随后在属性面板里改。
- 清单里有、画布上没摆的字段，列在字段列表的"未摆放"里，可以拖进画布。后端算的、只在后端用的字段可以一直不摆。
- 在画布上删控件只删 JSX，字段还留在清单里（转到"未摆放"）；要删字段在字段列表里删。防止误删一个已有数据的字段。
- 换控件：同一字段类型能用的控件之间切换（`TextField` ↔ `Textarea`），名字和能保留的属性都留着。
- 同一个字段摆了两次：问题列表里提示，不拦着。

#### 2.3 属性面板

- 分两组：**字段**（标签、说明、必填、长度、范围、选项、默认值）改的是清单；**控件**（占位文字、行数、步长……）改的是 JSX 上的属性。
- 每个组件登记一份属性说明：属性名、显示名、编辑方式（文字、数字、开关、单选、图标、条件），只列常见的几项。代码里写了面板不认识的属性，显示为"代码里还设置了 n 个属性"，原样保留。
- **常见的联动做成能点的**：字段的"显示条件"与"必填条件"，用条件构造器编辑，写进清单的 `visibleWhen`、`requiredWhen`（1.3）。更复杂的联动回到代码里写。

#### 2.4 接入方登记业务组件

在接入方的前端代码里登记（随模块表一起，不在线编辑），设计器的面板里就多出这些组件：

```ts
registerFormComponent({
  name: 'SupplierPicker',
  module: '@host/supplier', // 模块表里的名字，表单代码从这里 import
  label: '供应商',
  group: '业务',
  field: ['select'], // 能当哪些类型字段的控件；不写就是展示组件
  props: [{ name: 'scope', label: '范围', editor: { kind: 'select', options: ['active', 'all'] } }],
  defaults: { scope: 'active' },
});
```

- 设计器按"从哪个模块导入的哪个名字"认组件，不按标签名的文字，`import { SupplierPicker as Picker }` 也认得。
- 业务组件当字段控件时，值仍要符合字段类型（`select` 就是选项的值），后端照清单校验。

### 3. 画布与代码的对应、写回（已定，用户 2026-10-26）

参考 Onlook 一类"以代码为来源"的可视化编辑器的做法（据公开介绍：编译时给 JSX 元素注入标识、映射回源码位置、只改受影响的那段代码）。

一次设计操作的流程：

```
拖拽 / 改属性 → 算出要改的源码区间 → 改文字（只动这一段）→ 重新解析（几毫秒）→ 更新字段列表、组件树、选中
                                                         ↘ Worker 里重新编译（防抖）→ 预览换上新组件
```

实测（本机 Node，组件库的编译器 `@zerodep-dev/vue-tsx-pro-tsx/compiler`，浏览器的 Worker 里量级相同）：

| 表单规模 | 只解析 | 编译（热） | 首次编译（含加载编译器） |
| --- | --- | --- | --- |
| 40 个字段，约 100 行 | 1.2 ms | 23 ms | 163 ms |
| 150 个字段，约 320 行 | 4.4 ms | 72 ms | 264 ms |

所以每次改动都重新解析，结构信息总是最新的；编译放在 Worker 里防抖约 100 ms，拖拽中不卡。

#### 3.1 源码是唯一的状态

- 设计器的状态就是一份源码文字；字段列表、组件树、属性面板都是**解析出来的视图**，不另存一份模型，所以不会和代码不同步。
- 这份源码放在 CodeMirror 的编辑器状态里（代码页签没打开时也在）。设计操作就是对它的一次修改（一个 transaction），所以：
  - **撤销重做只有一个栈**：用 CodeMirror 自带的历史，设计操作每次单独成一步，打字按它的规则合并。不另做一套 `createHistory`，也不会出现两个撤销栈互相打架。
  - **代码页签开着时**，设计操作只把改动的那一段推给编辑器，光标、滚动位置都不丢（不整份替换）。
- 前端源码与后端源码是两份编辑器状态，各有各的撤销历史；后端代码不经设计器修改。
- 有没有未保存的改动：和上次保存的源码比一下。

#### 3.2 画布上的元素对应到源码

- 设计模式下编译时多加一个 Babel 插件，给每个登记过的组件的 JSX 元素加 `data-form-node` 属性；发布时的编译不加。
- 属性值是这个元素在组件树里的**路径**（从根元素起，每层是第几个子元素，如 `0.2.1`），而不是源码偏移：别处改了代码，路径不变，选中能留住。路径找不到了（这个元素被删了）就清空选中。
- 属性靠 Vue 的属性透传落到组件的根元素上；不往组件外面包一层，以免破坏要检查子元素的组件（标签页之类）。所以**登记组件的约定**加一条：根元素要接住透传的属性（组件库的组件按约定都接，待逐个实测）。
- 代码块（第 2 节）里的元素也会有标识，点中时选中的是整个代码块。

#### 3.3 写回

| 操作 | 改的是 |
| --- | --- |
| 插入组件 | 容器的子元素之间插一段新代码；缩进取同一层兄弟元素的缩进 |
| 删除 | 删掉这个元素的源码区间，连同它所在的整行 |
| 移动 | 删除加插入，算一步撤销 |
| 改控件属性 | 已有的属性只换值的那一段；新属性加在标签的最后一个属性后面；改回默认值就删掉这个属性 |
| 改字段 | `fields` 对象字面量里对应的那一项，做法同上 |

- 文件其余部分一个字符不动，手写的格式与注释都在。新代码由自己的小打印器生成（同组件演练场的 `props/code.ts`：属性多时一行一个，同 Prettier 的风格）。
- 不自动格式化整份代码。以后要"一键格式化"时按需加载 Prettier 的浏览器版（待定，先量体积）。

#### 3.4 画布

- **和设计器在同一个页面里渲染**，不放 iframe：主题、组件库、样式引擎都是同一份；iframe 要再加载一套运行时，弹层、主题切换也要跨框架处理。
  表单代码运行时出错由错误边界接住，画布上标出是哪个元素出错，设计器本身不受影响；死循环这种情况防不住，和在线写代码的其他地方一样，由作者自己负责。
- **两种模式**：
  - 设计：画布上盖一层透明的操作层，点击、拖拽都由操作层处理，表单里的控件不响应；选中框、插入位置的提示线都画在操作层上（位置取 `data-form-node` 元素的 `getBoundingClientRect`）。
  - 预览：去掉操作层，表单照常能填。可以选"按哪个流程的哪个节点看"，套用那个节点的字段权限（第 4 节），以及填写或查看两种模式。
- **能放进去的位置**：认得的容器（表单、分组、栅格、标签页的每一页）的子元素之间；代码块里面不能放。
- **重新编译后保留预览里填的值**：值放在设计器这一侧，换上新组件时作为初始值传进去。

#### 3.5 代码与设计两边同时改

- 在代码页签打字，防抖约 300 ms 后重新解析：解析成功，设计视图跟着更新；有语法错误，设计视图停在上次能解析的结果，顶上提示错误位置，**修好之前不能做设计操作**（否则会改在过期的位置上）。
- 编译错误（Babel 报的）与运行时错误都在问题列表里，点一条跳到代码里的位置。

### 4. 节点上的字段权限（已定，用户 2026-10-26）

同一张表单在不同节点上，谁能看哪些字段、能改哪些、哪些必填，写在流程定义的节点上，表单代码里不写节点判断。

#### 4.1 写法

```jsonc
// 流程级：一个流程一张表单（5.1）
"form": { "key": "purchase" },

// 人工节点上：只写权限
"form": {
  "default": "readonly",            // 没列出的字段按它；不写时：发起节点 editable，其他节点 readonly
  "fields": {
    "amount": "required",
    "supplier": "hidden",
    "lines": "editable",            // 明细表整体：能增删行、改各列
    "lines.price": "readonly"       // 明细表的某一列单独设
  }
}
```

权限四档，从严到宽：

| 权限 | 前端 | 后端 |
| --- | --- | --- |
| `hidden` | 不渲染 | **值不下发**（打开待办时就去掉，浏览器里看不到）；提交时忽略 |
| `readonly` | 显示，不能改 | 提交时忽略，用存着的值 |
| `editable` | 能改；必填按清单的 `required`、`requiredWhen` | 按清单校验 |
| `required` | 能改，而且必填 | 同上，另外一定要有值 |

- 键取自这张表单（流程发布时固定的那个版本，第 5 节）的字段清单；写了清单里没有的字段，流程发布时报问题。
- 明细表的列写成 `列表.列`，没单独写的列跟着明细表；明细表不是 `editable` / `required` 时不能增删行。

#### 4.2 和显示、必填条件合起来

一个字段在某个节点上最终怎样，按这个顺序算：

1. 节点上是 `hidden` → 隐藏，到此为止；
2. 清单的 `visibleWhen` 不成立 → 隐藏（值丢掉，同 1.3）；
3. 节点上是 `readonly` → 只读，**不算必填**（这一步填不了）；
4. 节点上是 `required` → 必填；是 `editable` → 按清单的 `required`、`requiredWhen`。

前端与后端都按这份顺序，规则放模型包（TS 与 Java 各一份，同一套样例）。

#### 4.3 不在待办里看表单的人

- 发起人看进度、抄送的人、历史记录、管理端：一律只读。流程定义上另有一份 `form.view`（只能写 `hidden` 或 `readonly`），用来对这些人藏起某些字段（例如内部的成本），没写就是全部只读。
- 管理员在管理端看全部字段（权限判断是接入方的扩展点）。

#### 4.4 前端怎样生效

- 表单容器按当前节点算好每个字段的权限，经 `context` 交给 `defineFlowForm` 生成的 `form.Field`：`hidden` 不渲染，`readonly`、`required` 转成组件库 `Field` 本来就有的
  `readonly`、`required` 属性（组件库的 `Field` 每个字段都能单独设，不用改组件库）。
- 自己在代码块里直接读写 `form.values` 的代码，经 `context.access('amount')` 取权限自己判断；即使写漏了，后端也会挡住（4.1 的后端一列）。
- 表单设计器的预览可以选"按哪个流程的哪个节点看"，套用这里的权限（3.4）。

#### 4.5 后端怎样生效

- **打开待办**：按节点权限过滤表单的值再下发，`hidden` 的不发。
- **提交**：只取 `editable` / `required` 的字段，其余用存着的值；再按 4.2 校验。后端代码的 `compute`（1.5）可以写任何字段，它是可信的。
- **留痕**：每次提交在流转记录里记下改了哪些字段（旧值、新值），审计时能查到谁在哪一步改了什么。

#### 4.6 流程设计器里怎样配

- 节点的属性面板列出这张表单的全部字段（明细表展开成列），每个字段选四档之一或"按默认"；可以"全部只读""全部可改"一键设好。
- 校验：引用了不存在的字段报错；清单里必填的字段在发起节点上是 `hidden` 或 `readonly`，提示"这个必填字段谁也填不了"。

### 5. 存储与版本（已定，用户 2026-10-26）

表的通用约定同 0001 的"表的草案"：`flow_` 前缀、雪花 BIGINT 主键、UTC 的 `DATETIME(3)`、可选的 `tenant_id`、不建外键、会变的行带版本列。

#### 5.1 一个流程一张表单

- 一个流程定义只引用一张表单，表单标识写在**流程级**：`definition.form = { key }`；各节点只写权限（`default`、`fields`）。
  4.1 的例子已按这条改过（2026-10-26）。
- 理由：同一个流程的各个节点看的是同一份业务数据，只是能看、能改的不同（第 4 节已经能表达）；某个节点要多填的东西（财务填付款日期）就是这张表单里的字段，在别的节点上隐藏。
  钉钉审批也是一个流程一张表单。各节点各用不同表单时，字段名会冲突、值也难合并。
- 审批意见、附件不进表单：它们属于"处理"这个动作，由审批面板收，记在流转记录里（0002 的人工节点）。

#### 5.2 表

| 表 | 作用 | 主要字段 | 索引 |
| --- | --- | --- | --- |
| `flow_form` | 表单本身 | key、名称、分类、状态（启用、停用）、最新版本号、创建与修改的人和时间 | 唯一（租户, key） |
| `flow_form_version` | 发布的版本，发布后不能改 | 表单、版本号、前端源码、前端编译结果、编译器版本、字段清单（JSON）、用到的模块（JSON）、后端语言（java / ts / 空）、后端源码、发布说明、发布人与时间 | 唯一（表单, 版本号） |
| `flow_draft` | 设计中的草稿：**和流程定义共用**，加一列种类（流程、表单） | 种类、key、内容（JSON：表单是前端源码与后端源码）、基于哪个版本、版本列、修改人与时间 | 主键（租户, 种类, key） |
| `flow_form_data` | 实例上表单的值，每个实例一行 | 实例、表单版本、值（JSON）、版本列 | 主键（实例） |

- 源码与编译结果用 `MEDIUMTEXT`（40 个字段的表单源码约 6 KB，编译结果同一量级）；字段清单与值用 MySQL 的 `JSON`。
- 草稿自动保存，版本列防两个人互相覆盖（同 0002 的草稿）。

#### 5.3 版本与引用

- 流程定义**发布时**把表单固定到当时的最新版本，写进定义的快照：`form = { key, version }`。表单再发新版本，已发布的流程和进行中的实例都不受影响。
- 表单发布后，设计器列出"还在用旧版本的流程定义"，可以一键把它们各发一个新版本改用新表单（只影响之后发起的实例）。
- 进行中的实例要换到新表单，走 0002 的"实例迁移到新版本"，不单独做。
- 被已发布的流程引用过的表单不能删除，只能停用（停用后新的流程定义不能再选它）；版本永远不删。

#### 5.4 编译结果与组件库升级

编译结果里会调用组件库运行时的辅助函数（样式绑定、符文），组件库大版本升级后旧的编译结果可能跑不了。所以：

- 每个版本记下编译它的编译器版本。审批页面加载时，大版本和当前运行时不一致，就**按需加载编译器**从源码重新编译（只在这种时候加载，平时审批页面不带编译器）。
- 管理端列出"需要重新编译的表单版本"，一键全部重编：浏览器里编译后写回编译结果（Nuxt 后端也可以在服务端编译）。源码不变，所以这不算改动已发布的版本。

#### 5.5 表单的值

- **不放进流程变量**，单独存在 `flow_form_data`。条件里写成 `form.字段名`（如 `form.amount`），流程变量照旧写变量名（1.3 已按这条改过）。
- 理由：
  - 流程变量是引擎推进用的（轮次计数、会签参与人），表单的值是用户的业务数据；分开之后，第 4 节的权限过滤只管表单的值，流程变量永远不发给浏览器，名字也不会冲突。
  - 实例行每推进一步都要锁、要改版本；大块的表单值不在这一行上。
- 条件构造器的字段列表分两组："表单"（从清单来）和"流程变量"（流程定义里声明的），用组件库 `ConditionField` 的 `group` 区分。
- 待办列表要显示的摘要（标题、金额）：流程定义里声明取哪几个字段，每次提交时抄进实例上已有的"展示用摘要"（0001 的 `flow_instance`）。按表单字段筛选实例，以后再加投影表（同 0001 对流程变量的说法）。
- 待办里的暂存（填了一半没提交）存在待办上，随引擎的表一起定。
- 要写业务表的，写在后端代码的 `submit` 里（1.5），与流转同一个事务。

#### 5.6 导出与导入

- 导出成一个 JSON 文件：key、名称、前端源码、后端语言与源码。不导出编译结果和字段清单。
- 导入时重新提取字段清单、重新编译（不信文件里带的东西）；后端语言和这个部署不一致（Java 的导进 Nuxt），去掉后端代码并提示。

### 6. 安全（已定，用户 2026-10-26）

#### 6.1 原则：不做隔离，安全交给接入方的框架

- **不做隔离**：前端代码跑在接入方已有的前端环境里，和页面上别的代码一样；后端代码跑在接入方已有的后端环境里，能拿到数据库连接、Bean、服务等全部权限。
- **页面与接口的安全由接入方自己的框架负责**：谁能打开设计器、谁能调保存与发布的接口、谁能看管理端，由接入方的登录、权限体系决定。引擎只提供扩展点，默认全部放行。
- **我们只做文档提示**，把风险写清楚（6.3），不替接入方做决定。
- "只能导入登记过的模块"（已定）是依赖管理，不是安全边界。

#### 6.2 提供的便利（默认都放宽，要收紧由接入方打开）

| 便利 | 默认 | 接入方怎样收紧 |
| --- | --- | --- |
| 权限扩展点：表单设计、后端代码、表单发布三个动作 | 全部放行 | 实现扩展点，接到自己的权限体系 |
| 发布页的差异对比（前端源码、后端源码、字段清单相对上一版） | 有这个按钮，看不看随意 | 配置成"看过才能发布" |
| 双人发布（发布人不能是这次改动的作者） | 关 | 配置打开 |
| 发布前的钩子（再次验证身份、走审批） | 没有 | 注册钩子 |
| 发布留痕（谁、什么时间、源码差异） | 开（只是记录，不拦任何操作） | — |
| 打开别人的草稿时先确认再运行预览 | 关，直接运行 | 配置打开 |
| 审批页面按脚本地址 `import()` 加载编译结果（不用 `eval`，页面的 CSP 不用开 `unsafe-eval`，可长期缓存） | 开 | — |
| Java 编译关掉注解处理器（`-proc:none`）：classpath 上的 Lombok 之类会在编译时执行，也会让编译结果不可预期 | 开 | 要用注解处理器时配置关掉 |
| 启动加载每张表单有时限，超时只停这一张 | 开（时限可配） | — |

- 发布时的编译结果由发布人的浏览器当场编译（不用作者存草稿时的那份），Nuxt 后端另外在服务端重编核对：这是发布流程本身的做法，不是额外的限制。

#### 6.3 文档里要提示的事

- 能发布表单代码的人等于能部署代码：前端代码以页面的全部权限运行，后端代码以应用的全部权限运行。
- 多租户时，所有租户的后端代码跑在同一个进程里，能读到别的租户的数据；后端代码的权限要不要给租户的管理员，由接入方决定。
- 后端代码的执行没有时限（在流转的事务里同步执行），死循环会占住线程；数据库语句有默认的超时。
- 后端代码 `load`、`actions` 返回给前端的东西不经权限过滤，由作者自己负责。
- 引擎自己保证的只有表单的值：隐藏字段不下发、提交只收能改的字段（4.5）。

### 7. 放在哪（已定，用户 2026-10-26）

#### 7.1 组件库里现在有什么

| 能力 | 现在在哪 | 是不是公开的 |
| --- | --- | --- |
| TSX 编译函数 `compile`（符文、样式绑定、Vue JSX、去类型，可以再加 Babel 插件） | `@zerodep-dev/vue-tsx-pro-tsx/compiler` | 是 |
| 在浏览器的 Worker 里编译（Babel 要的 `fs`、`assert` 等 Node 模块的空壳、Worker 的打包） | 文档站 `apps/docs/src/playground/`（`compile.worker.ts`、`node-shims/`） | 否 |
| 把 `import` 换成从模块表取、执行编译结果 | 文档站 `compile.ts` 的 `modulesToGlobals`、`run.ts` | 否 |
| 代码编辑器（CodeMirror 6，颜色字体取主题 token，Esc 后 Tab 移出焦点） | 文档站 `editor.ts`、`CodeEditor.tsx` | 否 |

编译器包自带的 `compile-worker` 是 Vite 在 Node 里用的线程池，不能在浏览器里用。

#### 7.2 建议：浏览器里编译与代码编辑器挪进组件库

文档站的演练场与表单设计器都要用这两样，放在组件库里只维护一份；Babel 在浏览器里跑要的那些空壳和打包细节，本来就属于编译器。

| 新的公开入口 | 内容 | 谁用 |
| --- | --- | --- |
| `@zerodep-dev/vue-tsx-pro-tsx/browser-compile` | Worker 里的编译（带好空壳）；把 `import` 改成"接收模块表的模块"的插件（6.2：审批页面按脚本地址 `import()`）；设计时直接执行的辅助函数 | 文档站演练场、表单设计器、审批页面的兜底重编（5.4） |
| `@zerodep-dev/vue-tsx-pro-ui/code-editor` | `CodeEditor` 组件：现在文档站的编辑器，语言由使用方传（TSX、Java、JSON……），对外给出 CodeMirror 的编辑器状态（3.1 要用它做唯一的状态与撤销） | 文档站、表单设计器，以后别的要写代码、写 JSON 的地方 |

- 两个都是单独的子路径：CodeMirror、Babel 体积大，只有用到的页面才加载，审批页面不带。
- 文档站改用这两个入口，删掉自己那份。
- 这会给组件库加两个公开入口，组件库要发一个小版本。
